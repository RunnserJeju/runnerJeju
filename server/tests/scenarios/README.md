# 러닝위크 지급 시나리오 테스트

코스 완주 인증 한 번에 무엇이 지급되는지(스탬프·일반 쿠폰·빙고 리워드·스페셜 쿠폰)를 사용자 시나리오로 돌려 보고, 결과를 흐름도와 함께 HTML 리포트로 만든다. 진짜 Postgres를 Docker로 띄워서 실제 지급 코드(`app/routers/verifications.py`의 완주 인증)를 그대로 호출한다.

## 결과 보기 (테스트를 돌리지 않는 사람)

GitHub → **Actions** → **시나리오 테스트** → 실행 하나를 연다.

- 페이지 위쪽 요약표: 통과 수, 실패한 시나리오와 어디서 달랐는지.
- 페이지 아래 **Artifacts → scenario-report**: 내려받아 압축을 풀고 `scenario-report.html`을 브라우저로 연다. 인터넷 없이도 열린다.

`server/` 아래가 바뀐 push(main)·PR마다 자동으로 돈다. 직접 돌리려면 Actions 탭의 **시나리오 테스트 → Run workflow**.

## 로컬에서 돌리기

### 준비 (한 번만)

1. **Docker Desktop**을 설치하고 켠다. 확인: `docker version`에 `Server:` 항목이 나와야 한다.
2. **uv**를 설치한다. 확인: `uv --version`.
3. 의존성 설치:
   ```
   cd server
   uv sync
   ```

### 실행

```
cd server
uv run pytest -m scenario                 # 끝나면 리포트 위치를 출력
uv run pytest -m scenario --open-report   # 끝나자마자 브라우저로 연다
```

DB는 테스트가 알아서 띄우고 끝나면 지운다. 팀 공유 DB(`DATABASE_URL`)에는 붙지 않는다. 처음 한 번은 DB 이미지(`postgis/postgis:16-3.4`)를 내려받느라 몇 분 걸리고, 그 뒤로는 10초 안팎이다.

**성공하면** 마지막에 이렇게 나온다:

```
------------------------- 시나리오 리포트 -------------------------
.../server/test-reports/latest/scenario-report.html
24 passed, 323 deselected in 10.36s
```

(시나리오 23개 + 시나리오 이름 검사 1개. 숫자는 시나리오를 더하면 바뀐다.)

평소의 `uv run pytest`는 시나리오 테스트를 빼고 돈다(Docker 없이 323개). 시나리오는 `-m scenario`를 줄 때만 돈다.

### 리포트 파일

| 위치 | 내용 |
|---|---|
| `server/test-reports/latest/scenario-report.html` | 방금 실행한 결과. 실행할 때마다 덮어쓴다 |
| `server/test-reports/latest/summary.md` | 요약표(CI가 실행 페이지에 띄운다) |
| `server/test-reports/<날짜_시각>/` | 실행별 보관본. 최근 10개만 남긴다 |

git에는 올라가지 않는다(`.gitignore`). 다른 사람에게 보여 줄 때는 HTML 파일 하나만 보내면 된다.

## 리포트 읽는 법

- **왼쪽 흐름도**: 완주 인증 한 번이 지나가는 길. 맨 위 "모든 사용자"는 누구나, 점선 영역 "러닝위크 참가자 전용"은 참가자가 기간 중일 때만 거친다. 그 안의 ①~④ 단계는 차례로 **모두** 거친다 — 한 단계에서 받을 게 없으면 "건너뜀"으로 다음 단계로 간다.
  - 노란 육각형: 조건 / 초록: 받는 것 / 회색: 끝·미지급
  - **노드 모서리 숫자**: 그 노드를 지나는 시나리오 수. 초록 = 모두 통과, 빨강 = 실패가 있음, 회색 점선(0) = 어떤 시나리오도 안 지나감(테스트 빈 곳).
- **오른쪽 시나리오 목록**: 누르면 흐름도에 그 시나리오가 지나는 길이 켜지고, 사건별 타임라인(그때 받은 것, 5×5 빙고판 상태)이 펼쳐진다. 흐름도의 노드를 누르면 그 노드를 지나는 시나리오만 남는다.
- 실패가 있으면 첫 번째 실패 시나리오가 펼쳐진 채로 열린다. 빨간 단계에 "기대"와 "실제"가 같이 나온다.

## 실패했을 때

1. **어느 시나리오의 몇 번째 사건인지** 본다(터미널 출력 또는 리포트의 빨간 단계).
2. 기대가 틀렸나, 구현이 틀렸나를 가른다. 시나리오의 기대는 사람이 적은 "의도"다 — 지급 규칙을 일부러 바꿨다면 시나리오를 고치고, 아니라면 구현 버그다.
3. 테스트가 시작조차 못 하면:
   - `Cannot connect to the Docker daemon` 류 → Docker Desktop이 켜져 있는지 확인.
   - `마이그레이션 실패` → 빈 DB에서 `alembic upgrade head`가 깨진 것. 가장 최근 마이그레이션부터 본다.

## 시나리오 고치기·더하기

| 파일 | 역할 |
|---|---|
| `scenarios_user.py` | 사용자 시나리오(참가자가 겪는 일) |
| `scenarios_ops.py` | 운영 시나리오(운영자 설정·시스템 동작에 따라 달라지는 일) |
| `scenario_model.py` | 시나리오를 적는 틀: 시작 상황(`Setup`)과 사건(`Complete`, `Join`, `Prefill`, `SetCoupon`, `AdminIssue`) |
| `scenario_flow.py` | 흐름도(노드·화살표·단계 상자)와 시나리오가 지나는 길의 조각 |
| `scenario_world.py` / `scenario_runner.py` | DB에 상황 만들기 / 시나리오 실행·비교 |
| `scenario_report.py` | HTML 리포트·요약 만들기 |

시나리오 하나는 이야기 하나다 — 시작 상황 → 사건(순서대로) → 사건마다 **새로 받은 것**:

```python
Scenario(
    "B1", "B. 일반 쿠폰", "완주하고 일반 쿠폰 당첨",
    "참가자가 새 코스를 완주하고 일반 쿠폰 추첨에 당첨된다.",
    Setup(coupons={"general": WIN}),             # 일반 쿠폰 활성화, 추첨 결과는 당첨으로 고정
    [Complete(0, gets=[BASIC, RW, GEN])],         # 1번 코스 완주 → 기본·러닝위크 스탬프, 일반 쿠폰
    nodes=GEN_WIN + NO_LINES,                     # 흐름도에서 지나는 길
)
```

- **기대(`gets`)는 구현을 보고 베끼지 말고 의도대로 적는다.** 구현을 베끼면 같은 버그를 서로 맞다고 한다.
- 쿠폰은 적은 것만 활성화된다. 추첨 결과는 `WIN`(당첨)·`LOSE`(낙첨)로 고정한다 — 확률 자체는 검사하지 않는다.
- `Prefill([칸들])`은 그 칸의 코스를 실제로 차례로 완주한다(그동안 받은 것은 비교하지 않는다). 빙고 칸 번호는 0~24이고 코스 번호와 같다.
- `nodes`는 손으로 단다. 지급 규칙(구현)이 바뀌면 `scenario_flow.py`의 흐름도도 손으로 고친다. 흐름도에 없는 노드 이름을 쓰면 `test_scenario_ids_are_unique_and_nodes_exist`가 실패한다.
