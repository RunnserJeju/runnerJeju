
# 경로 검증

러닝 경로가 코스를 따라 달린 것인지 판정하는 로직의 설계 기록. 서버 분리 계획과 API 계약은 [architecture.md](architecture.md)의 "경로 검증" 절에 있고, 여기는 **판정 자체를 어떻게 정확하게 만드는가**를 다룬다.

## 우선순위

**정직하게 달린 사람이 정확하게 matched를 받는 것이 먼저다.** 치팅 방지(가짜 GPS, 좌표 재생, 이동수단)는 그 다음 단계로 미룬다 — 아래 "나중에 할 일" 참고. 같은 이유로 파라미터는 오탐(정직한데 mismatched)을 피하는 쪽으로 넉넉하게 잡고 시작한다.

## 판정 로직

**스탬프 기준은 "완주"가 아니라 "코스의 85%를 달렸는가"다(제품 결정).** 종료 지점에 도달하지 못해도 85%를 채웠으면 인정한다.

```
match_rate = 코스 리샘플 점 중 러닝 경로가 tolerance 안에서 지나간 점의 비율

matched    = match_rate ≥ 85%            (궤적 일치 — 코스 점의 85% 이상을 지나감)
           ∧ 주행 거리 ≥ 코스 거리의 85%   (실제 주행량 — 왕복 코스의 편도 주행 차단)
```

같은 85% 기준을 두 가지 측정으로 확인하는 구조다. 거리 조건이 따로 필요한 이유는 왕복 코스 때문이다(아래 참고).

**시작/종료 지점 근접 조건은 검토 후 채택하지 않았다.** 한때 구현했다가 뺐다 — "종점 60m 이내를 지나야 인정"은 기준을 사실상 완주로 만드는데, 기준은 85%다. 점대점 코스에서 종점 900m 전에 멈춘 러닝(커버리지 85%)이 인정되는 것이 의도된 동작이다. 나중에 "완주 전용 스탬프" 같은 기능이 생기면 그때 다시 꺼낼 수 있게 이유를 남겨둔다.

### 코스는 등록 시 15m 간격으로 리샘플링한다 (구현됨)

GPX 원본은 사람이 그린 것이라 점 밀도가 불균등하다(사계해안도로: 평균 30m, 최장 252m — 곡선은 촘촘, 직선은 성김). 이대로 "커버된 점 개수 비율"을 매칭률로 쓰면 점이 몰린 구간에 가중치가 쏠려서, 사용자가 이해하는 "코스 거리의 몇 %"와 어긋난다. 균등 간격이면 **점 개수 비율 = 거리 비율**이 된다.

- 리샘플은 코스 등록(`PUT /courses/gpx`) 시 1회만 하고 결과를 `courses.path`(JSONB)에 저장한다. 검증은 매번 계산하지 않고 DB에서 읽는다. 클라이언트도 같은 배열을 받아 지도 그리기와 (예정) 실시간 커버리지의 기준점으로 쓴다 — 서버와 클라가 정확히 같은 점을 보므로 어긋날 수 없다.
- 원본 GPX 점은 DB에 저장하지 않는다. 거리·고도·순환 판정은 파싱 시점에 원본으로 계산해 별도 컬럼에 저장한다(리샘플은 코너를 살짝 질러가 0.25% 짧아지므로 공식 거리로 쓰지 않는다).
- 구현: `geo.resample_path`, `gpx.RESAMPLE_INTERVAL_METERS`, 사계해안도로 6.2km 기준 185점 → 417점(약 18KB).
- **기존 DB의 코스에는 원본 경로가 남아 있다. `tools/push_courses.py` 재업로드로 갈아야 한다.**

### 매칭은 점-대-점이 아니라 점-대-선분으로 (구현됨)

러닝 기록의 GPS 점 사이가 벌어진 구간(신호 끊김 등)에서, 코스 점과 기록 *점*의 거리만 재면 실제로는 그 사이 선 위를 지났는데도 놓친다. 그래서 `coverage_ratio`는 코스 점에서 러닝 경로 *꺾은선*까지의 최단거리로 잰다(`verification._near_polyline` — geo의 선분 거리와 같은 계산이지만 무의존 원칙 때문에 재구현).

연산량 대비로 좌표를 지역 평면(m)에 한 번만 투영하고, 먼 세그먼트는 바운딩박스로 걸러낸다. 실측(코스 417점 × 러닝 1,245점): 완주 케이스 13ms, 완전 불일치(최악) 69ms — 검증 서버 분리가 급하지 않은 수준이다.

### 왕복 코스의 한계와 대책 (구현됨)

사계해안도로는 같은 길을 되돌아오는 왕복 코스라, **편도만 달려도 커버리지가 100%가 된다**(복로가 왕로의 30m 안에 있으므로). 커버리지만으로는 편도와 완주를 구분할 수 없다 — `test_verification.py`에 이 특성이 테스트로 기록되어 있다. **편도 주행을 막는 것은 거리 하한(85%)이다** — 편도는 커버리지 100%여도 주행 거리가 코스의 절반이라 탈락한다.

## 파라미터

| 값 | 현재 | 근거 |
| --- | --- | --- |
| tolerance | 30m | 스마트폰 GPS 오차 5~10m(개활지)·20~30m(건물/나무 옆), Strava 세그먼트 매칭 마진 약 20m. 오탐 회피 우선이라 넉넉한 쪽. |
| threshold | 85% | 스탬프 기준 그 자체("코스의 85%"). 신호 대기·장애물 회피 같은 정상 이탈도 이 여유 안에서 흡수된다. |
| 거리 하한 | 85% | threshold와 같은 기준의 다른 측정. 왕복 코스 편도 주행 차단. |
| 리샘플 간격 | 15m | 기록 간격(5m) < 리샘플 간격 < tolerance 관계를 지켜야 한다. |
| 기록 간격 | 5m | 클라 `distanceFilter: 5`. 정지 시 GPS 흔들림이 거리에 쌓이는 것 방지. |

클라이언트는 서버와 **같은 두 숫자를 실시간으로 계산**한다(`RunTracker`).

- 진행률 바 = min(커버리지, 거리 비율). 커버리지만 보여주면 왕복 코스에서 반환점에 이미 100%가 떠서 혼란스럽다 — min이 그걸 잡아주고, 코스를 벗어나면 바가 멈춘다.
- 두 숫자가 모두 85%를 넘으면(`hasReachedCourseGoal` — 서버 인정 기준과 동일) 러닝 화면에 **완주 버튼**이 나타난다. 자동 종료는 하지 않는다 — 더 달리고 싶은 사람을 끊고, 조건 판정의 잔버그가 곧바로 "종료를 못 하는 버그"가 되기 때문. 종료는 항상 사용자 버튼으로만 하고, 버튼이 안 떠도 일시정지 → 종료 경로가 늘 있다.
- 버튼 조건이 서버 기준과 같으므로 "완주 버튼 눌렀는데 mismatched"는 구조적으로 불가능하다. 상수 값은 `RunTracker`와 `verification.py`가 같아야 한다(양쪽 주석 참고).

이 값들은 실측으로 검증된 적이 없다. 실제 기기로 코스를 달린 기록이 쌓이면(정상 이탈이 실제 몇 m·몇 %인지) 그 분포를 보고 조정한다. 그 전까지는 넉넉한 값을 유지한다.
